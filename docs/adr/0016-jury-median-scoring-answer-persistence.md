# 裁判团中位数判分 + 答案持久化（eval_answers、eval_judge_scores）

评估体系两个既有约定在「三段异步管线 + 三裁判」重构下不再成立：① **单裁判**——一个 judge_model 的个体偏差与单点故障直接进分数，裁判不可达按 Hub 发生（GH #155），全局单值配置不匹配多 Hub；② **答案不独立持久化**——`evalSample` 内同步走完「答题→裁判」，答案只活在内存，解耦后裁判段崩溃即丢已付费答案。同时，三中位数与单裁判是不同的判分尺子，按 ADR 0007/0008 的「跨时间可比」原则必须口径版本化，不能无声换尺。

**决策：**

1. **裁判团中位数判分**：judge 型 case 的每个样本由 3 个裁判独立打分，样本分 = 中位数；残缺票按 3→中位、2→均值、1→自身、0→null 降级，裁判失败绝不计 0（W7 延伸）。case 分 = 样本中位数的均值（沿用 avg-of-samples）。rule 型 case 不走裁判团。
2. **判分口径升级为 Verdict Profile `v3`**（v1 = 仅 trim 单裁判，v2 = 归一化管道单裁判，v3 = 归一化管道 + 裁判团中位数）；存量结果不回刷，报告/趋势/告警在 v2→v3 处形成断点，机制与 ADR 0008 完全一致。`eval_runs` 新增 `jury_models` 快照列（JSON：策略 + 槽位模型），`judge_model` 旧列保留只读兼容。
3. **答案与逐裁判分独立持久化**：新表 `eval_answers`（每 sample 一行，答题成功即落库）与 `eval_judge_scores`（每 answer × 裁判槽位一行）；裁判队列据此在崩溃后重建，已判票不重判。`eval_results` 仍是唯一对外结果行，新表是过程明细。

**承重墙四问（W2 存储层 + W7 评估不可变性）：**

1. **为什么必须改？** 不改的代价：三段解耦无法成立（答案无落点，崩溃丢答案 = 丢已付费调用）；三裁判分值无处存（逐裁判展示与中位数审计不可能）；口径无声变化会破坏跨时间可比（W7 核心价值）。改法是只加不删，存量行语义不变。
2. **影响哪些调用方？** 直接：`evaluator.evalCase`/`evalSample`（写入路径切换为聚合器）、`store`（迁移 + 新表 CRUD）、`store.Open`（全量用户库自动迁移）。间接：报告/趋势读取（需识别 profile v3 断点）、分数大跌告警（v2→v3 断点处跳过）、报表 API（逐裁判分/成本/TPS 透出）、`isolation_test.go` sweep（新 list 接口登记）。
3. **替代方案？** ① 逐裁判分塞 `eval_results` JSON 列——否决：行宽膨胀、逐裁判查询/聚合困难、样本多行语义混乱；② 裁判队列纯内存不落库——否决：崩溃丢答案丢钱，违背用户决策 3；③ 不换 profile 直接换尺——否决：违反 ADR 0007 断点纪律。新表是 W2「只加不删」约束下的最小迁移。
4. **回归测试什么？** 一层：迁移幂等 + 旧库升级后新旧 Run 共存渲染；中位数降级规则四档；崩溃重建裁判队列不重判；profile v3 写入与断点断言。二层：`internal/evaluator`、`internal/store` 全量回测；报告/趋势/告警断点行为。三层：`make test` 全量（核心业务闭环）。

**后果：** 评估批次成本上升（judge 型 case 裁判调用 ×3，spec 0020 决策 4 已论证可接受）；新表只增不删，长期体积增长由既有 rollup/清理机制兜底（必要时另立票）；v2→v3 断点之后，跨断点涨跌比较与分数大跌告警按既有断点口径跳过。
