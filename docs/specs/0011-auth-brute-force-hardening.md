# 0011 — 认证防爆破加固(登录渐进延迟 + 爆破告警 + 代理头信任修复)

## 背景

生产实例已上线(spec 0008,Caddy 自动 HTTPS,公网可达)。用户担心管理台被爆破或遭反复登录尝试。现状盘点:

**已有防线(不动):**
- per-IP 登录限流:5 次/分钟(burst 5),超限 429(`ratelimit.go`);
- 统一错误消息防用户名枚举;每次登录成败落审计(含 IP 与失败原因);
- bcrypt 哈希 + 最少 8 位密码;HMAC 签名会话 cookie(HttpOnly/SameSite=Lax/HTTPS 下 Secure);
- 安全头 + CSP;限流表 fail-closed 防内存喷溅。

**三个真实缺口:**
1. **代理头信任未接好(最紧迫):** 生产在 Caddy 之后,但 `TRUST_PROXY` 未在任何部署脚本/.env 模板中设置,`clientIP` 落到 Caddy 的地址——全站共享一个登录桶(攻击者可持续占满桶、把合法管理员的登录也挤掉,变相 DoS),审计 IP 全部失真。且代码注释已写明前置代理必须**替换**客户端自带的 `X-Forwarded-For`;Caddy 自 v2.7(2023)起默认已忽略/删除客户端自带 XFF 再写直连对端 IP(旧版默认为**追加**,伪造的最左跳会成为权威值;生产 Caddy ≥2.10 默认已安全),但仍需在 Caddyfile 模板显式写 `header_up` 把替换契约固定下来——版本无关,并防未来 trusted_proxies 配置漂移。
2. **只有 per-IP 限流,没有 per-账户防护:** 分布式爆破(换 IP 打同一用户名)可绕过 per-IP 桶。
3. **有审计、没有告警:** 爆破发生时只躺在审计表里,没人知道。

## 决策总览

1. **防护范围(用户裁决):** 修配置 + 应用层加固。不做网络层隔离(/admin 公网保持可达),不做 2FA,不动密码策略与会话机制。

2. **代理头信任修复(配置/部署面,不改应用语义):**
   - 两条部署线(生产 Caddy / 测试线反代)的代理配置模板统一保证 **替换** 客户端自带的 `X-Forwarded-For`(Caddy 用 `header_up X-Forwarded-For {remote_host}` 显式固定替换语义;测试线 nginx 的 `proxy_set_header` 用 `$remote_addr` 即是替换语义,补齐确认);
   - 有反代的线注入 `TRUST_PROXY=true`;**实测无反代的线(容器直接暴露)保持 `false`,绝不注入**——直接暴露时信任 XFF 等于把限流键与审计 IP 交给客户端伪造,比不开更糟(2026-07-28 实施时实测:测试线 192.168.1.101 无反代,故只加注释不注入);
   - 存量生产机的 Caddyfile 与容器环境随下一次部署一并修正(经 deploy.sh 路径,不手工改服务器);
   - 验收:登录审计记录真实客户端 IP;单 IP 超限只影响该 IP(不再全站共享桶)。

3. **per-账户渐进延迟(应用层核心):**
   - 按**用户名字符串**计数(不区分用户是否存在——否则行为差异会泄露用户名有效性,与现有统一错误消息口径一致);
   - 内存态滑动窗口:同一用户名 **10 分钟内失败 ≥5 次**后,后续**失败响应**做指数退避延迟:2s → 4s → **8s 封顶**;窗口滑出后计数自然衰减;
   - **先验密码,后罚延迟:延迟只落在密码错误的响应上,正确密码永远立即放行**——合法管理员零感知,攻击者对合法用户零伤害(否决账户锁定方案的关键理由:锁定会被用来持续锁死管理员);
   - 登录成功即清零该用户名的计数;
   - 内存态即可,重启清零是可接受代价(重启本身是低频事件,且 per-IP 限流仍在);不进 store,无 schema 变更;
   - 计数 map 与 ipLimiter 同纪律:硬上限 + 定期清扫,防用户名喷溅撑爆内存;达到上限时新用户名跳过计数(per-IP 限流仍兜底),不 fail-closed 误伤;
   - 并发界:睡眠中的 goroutine 由 per-IP 登录限流约束,最坏情况(分布式大喷溅)约数千个挂起 goroutine,Go 可承受,登记为已知接受界。

4. **爆破告警(应用层,补「出事不知道」):**
   - 实例级口径:**10 分钟内全站登录失败 ≥10 次**触发一次 Lark 告警,**冷却 30 分钟**(冷却期内不重复发);
   - 告警走 server 持有的**唯一 alerter.Evaluator 实例**(W5:全进程单实例),新增认证域方法,webhook 配置沿用现有 settings,不建第二条告警链路;
   - 告警内容:失败次数 + 窗口 + 被尝试最多的用户名(前 3)+ 来源 IP(前 3)——与审计同级信息;**绝不含密码**;Lark webhook 地址不进任何日志(W6);
   - 防抖用内存冷却即可:登录计数本就是内存态、重启清零,不适用 W5「懒状态重建/落事件防重发」语义(该语义针对端点状态机跨重启不重复告警);若发送失败,记应用日志,不重试轰炸。

5. **可测试性接缝(沿用 W1 唯一接缝,不新增):**
   - 延迟表经 server option 注入(与 `WithRateLimits` 先例同构),测试注入毫秒级延迟表,黑盒断言行为;
   - 不 mock 内部模块,不断言内部状态——测试只观察 HTTP 响应(状态码、响应时间量级、告警副作用)。

6. **「反复登录」的另一层含义(澄清登记):** 成功登录不受任何延迟影响,重复成功登录无害(每次签发新 cookie)。若未来需要「强制全员下线」,旋转 `SESSION_SECRET` 即可(已有机制,本 spec 不动)。

## 数据模型变更

无。登录失败计数与告警冷却均为进程内存态,不进 SQLite。

## 承重墙影响分析

本 spec 不修改任何承重墙,只消费:

- **W1(唯一测试接缝):** 全部新测试走既有黑盒接缝(httptest + 真 SQLite 临时库),延迟表经 server option 注入,与 `WithRateLimits` 先例同构,不开新接缝。
- **W5(状态机与告警防抖):** 认证告警复用 server 持有的唯一 `alerter.Evaluator` 实例,不创建第二个告警发送方;新增的是「认证域告警方法」,端点状态机与既有告警路径零改动。W5 的懒重建/落事件语义针对跨重启的端点状态机,认证域为内存态,明确不适用(见决策 4)。
- **W6(凭证边界):** 告警与日志绝不含密码与 webhook 地址;延迟机制不改变统一错误消息口径,不引入用户名枚举旁路(对不存在用户同样计数、同样延迟)。
- **W4(调度器时钟注入):** 登录延迟是请求路径上的响应延迟,非周期作业,不属于调度器管辖;测试加速经 option 注入延迟表而非假时钟,不触碰 W4 语义。

## 测试决策

好测试 = 只观察外部行为(HTTP 状态码、响应时间量级、告警副作用),不断言内部计数器状态。全部测试在 W1 接缝(httptest + 真 SQLite 临时库)上:

1. 同一用户名连续失败达到阈值后,失败响应出现可观测延迟(注入毫秒级延迟表);阈值前无延迟;
2. 超过阈值后,**正确密码仍立即放行**(无延迟、返回成功),且成功后该用户名计数清零(后续失败回到无延迟);
3. 不存在的用户名与真实用户名在失败路径上行为完全一致(状态码、延迟、错误消息无差异);
4. 实例级失败次数达到告警阈值时,Lark 发送方被调用一次;冷却期内继续失败不重复发送;
5. per-IP 登录限流行为不变(现有用例回归);
6. 代理头信任:TRUST_PROXY 开启时审计记录 XFF 第一跳(替换语义由部署模板保证,应用层行为已有 `clientIP` 测试先例)。

**测试先例:** `auth_test.go`(登录成败/禁用/统一错误)、`security_test.go`(限流与安全头)、`alerts_test.go`(告警副作用断言)、`ratelimit.go` 的 option 注入模式。

**部署面验收(非单测):** 配置修复随下一次部署生效后,实测两条线——失败登录的审计记录显示真实客户端 IP;同一来源超限不影响其他来源。

## 范围外

- TOTP/二步验证;
- 网络层隔离(Caddy/nginx 按路径限制管理台来源);
- 密码策略提升(最少 8 位维持不变);
- 会话机制变更(TTL、滑动续期、按会话吊销);
- per-IP 限流档位调参(5/30/1200 维持现状);
- 账户锁定及 CLI 解锁通道(被渐进延迟方案否决)。

## 备注

- 攻击者视角的残余风险登记:渐进延迟把分布式爆破成本拉到「每 IP 每次尝试数秒」,8 位密码空间在可接受安全界内;若未来暴露面扩大(如管理台对更大范围开放),再评估网络层隔离与 2FA。
- 本 spec 落地后建议走一遍 `/code-review` 复核 W5/W6 消费口径。
