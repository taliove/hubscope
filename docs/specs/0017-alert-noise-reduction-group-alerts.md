# Spec 0017:告警降噪(聚合窗口 + 分组告警 + 静默时段)与分组 24h 展示

> 经 /grill-with-docs 逐决策确认(2026-07-30),术语已登记 CONTEXT.md「Language — 告警」。
> 本 spec 扩展 W5(状态机与告警防抖),实施阶段须附 ADR 0014(承重墙四问见文末)。

## Problem Statement

运维读者当前面临三个问题:

1. **告警轰炸**:Hub 侧故障时,其下多个端点在同一轮探测中接连 down,每个端点立即发一条 Lark 告警——一次故障刷 N 条消息,真正重要的信息被淹没;恢复时同样刷屏。
2. **夜间打扰**:凌晨的告警与白天的告警同等响亮。夜间故障大多无法即时处置,但消息照发,长期下去告警可信度被磨损(狼来了)。
3. **分组健康不可见**:状态板按厂商/能力/协议分组时,组标头只有「24h 可用率 + 均延」两个标量,没有 24 格分段条;整组的时间分布形态(几点开始炸的、是否已恢复)要逐卡展开才能看到。

## Solution

1. **聚合窗口(Alert Window)**:告警发送前加 60 秒缓冲,窗口内多个端点的同类迁移合并为一条按 Hub 归因分组的聚合消息——「Hub A(疑似 Hub 侧故障):模型 x/y/z」,有主有次。
2. **分组告警(Group Alert)**:新增厂商维度的整组故障告警(≥50% 且 ≥2 端点 down 触发)。组告警 open 后吸收组内端点告警,整组故障从「N 条端点消息」收敛为「1 条组消息 + 明细」。
3. **静默时段(Quiet Hours)**:可配置的每日静默窗口(默认关闭,如 23:00–07:00)。期内不发送,结束时发一条摘要,只列当时仍故障的端点/组——夜间不打扰,醒来不错过。
4. **分组 24h 分段条**:分组标头下方新增组级 24 格分段条,折叠恒显,前端按批 59 口径从组内端点 dots 聚合,零 API 变更。

## User Stories

### 分组 24h 展示

1. 作为状态板读者,我希望按厂商分组时在组标头下方看到该组的 24h 分段可用率条,以便不展开任何卡片就能判断这个厂商今天的健康形态。
2. 作为状态板读者,我希望 hover 分段条的某个小时格能看到该时段「成功 X/N」的精确读数,以便确认异常时段。
3. 作为状态板读者,我希望折叠分组时分段条仍然可见,以便收起卡片矩阵后仍能扫读各组健康。
4. 作为状态板读者,我希望无探测数据的小时格显示为灰色,以便区分「无数据」与「全失败」。
5. 作为状态板读者,我希望切换分组维度(厂商/能力/协议)后分段条按新分组重算,以便各维度视图一致可用。
6. 作为状态板读者,我希望暗色模式下分段条三档着色仍可分辨,以便夜间投屏可读。

### 分组告警

7. 作为运维,我希望某厂商组内 ≥50% 且 ≥2 个端点 down 时收到一条「厂商组故障」告警,而不是 N 条独立的端点告警,以便一次看清是上游/厂商级故障。
8. 作为运维,我希望组告警消息内按 Hub 分组列出故障端点明细,以便先定界(哪个 Hub)再定点(哪个模型)。
9. 作为运维,我希望组告警 open 期间组内新增 down 的端点不再单独发告警,以便故障演变过程不刷屏。
10. 作为运维,我希望组告警 open 期间组内端点的恢复也不单独发消息,以便恢复过程同样安静。
11. 作为运维,我希望组占比回落到 50% 以下时收到一条组恢复消息,列出已恢复与仍故障的端点,以便知道还有哪些尾巴要追。
12. 作为运维,我希望单端点组永不触发组告警,以便小组不产生语义重复的噪音(那是端点告警的职责)。
13. 作为运维,我希望组告警触发前已经发出的端点告警不受影响,以便已送达的信息保持原样(不可收回,既往不咎)。
14. 作为运维,我希望服务重启后组告警状态正确重建、不重复告警,以便发布重启不制造假警。

### 聚合窗口

15. 作为运维,我希望多个端点在同一轮探测中接连 down 时只收到一条聚合消息,以便一次故障只占我一次注意力。
16. 作为运维,我希望聚合消息按 Hub 归因分组并标注「疑似 Hub 侧故障」,以便第一眼完成故障定界。
17. 作为运维,我可以接受单端点故障告警最多延迟 60 秒,以便换取多点故障时的聚合收益。
18. 作为运维,我希望同一窗口内的多个恢复也合并为一条消息,以便恢复同样不刷屏。
19. 作为运维,我希望聚合发送失败被记录(sent_ok=false)但不重发,以便故障期不产生重试轰炸。
20. 作为运维,我希望同一窗口内既有 down 又有恢复时分卡发送,以便坏消息与好消息不混在一张卡片里。

### 静默时段

21. 作为运维,我希望配置静默时段(如 23:00–07:00)后夜间不再被告警消息打扰,以便告警长期保持可信度。
22. 作为运维,我希望静默期发生的故障在静默结束时以一条摘要告知——只列当时仍故障的端点/组,以便醒来第一眼看到还需要处置什么。
23. 作为运维,我希望静默期内自愈的故障不出现在摘要里,以便摘要不包含任何无需行动的信息。
24. 作为运维,我希望静默期内的 score_drop(评估分数骤降)告警也延迟到静默结束,以便夜间完全安静。
25. 作为安全管理员,我希望 login 爆破告警不受静默约束、即时送达,以便安全事件不错过处置窗口。
26. 作为管理员,我希望静默默认不启用,以便未配置时行为与现状完全一致。
27. 作为管理员,我希望在管理台设置页配置静默的起止小时与启停,以便不改配置文件、不重启服务。
28. 作为审计者,我希望静默期内的事件照常落库,以便事后在告警历史中完整复盘。
29. 作为运维,我希望摘要为空(无未恢复故障、无静默期 score_drop)时不发任何消息,以便安静是真正的安静。

### 告警历史

30. 作为审计者,我希望告警历史中能区分 down/recovered/group_down/group_recovered/batch/quiet_summary 各类型,以便复盘时看懂每次发送的形态。
31. 作为审计者,我希望告警历史能看到实际发出的聚合消息原文,以便核对当时读者看到的内容。

## Implementation Decisions

### 数据层(internal/store)

- `alert_events` 新增**可空列 `group_key` TEXT**(只加不删迁移,随 `store.Open` 自动升级);分组告警事件以此列承载厂商名,`endpoint_id` 为 NULL。
- 新事件 kind:`group_down` / `group_recovered`(组状态迁移)、`batch`(一次聚合发送的实际投递)、`quiet_summary`(静默结束摘要投递)。既有 `down` / `recovered` / `score_drop` / login 类 kind 不变。
- 新 store 方法:flush 后回写事件 `sent_ok` 的更新方法;按 `group_key` 查最新组事件(组告警懒重建);查询当前仍 open 的告警(端点:最新 down/recovered 事件为 down;组:同理)供静默摘要。
- settings 新键:`quiet_hours_enabled`(默认 false)、`quiet_hours_start` / `quiet_hours_end`(0–23 整数小时,服务器本地时区,支持 23→7 跨日;start==end 视为未启用)。

### 告警器(internal/alerter)——核心变更

- **发送与状态判定解耦**:transition 判定时刻立即落 per-endpoint 事件(`sent_ok=false` 占位,含义「投递未确认」)并翻转内存 alerted flag——**W5 懒状态重建语义不变,重启不重复告警**;随后迁移进入窗口缓冲而非立即发送。
- **聚合窗口**:首个 pending 迁移开 60s 窗口;flush 时按 kind 分两卡(down 卡 / recovered 卡),卡内按 Hub 分节;发送后回写各事件 `sent_ok` 并落一条 `batch` 事件(message = 实际发出的聚合文本,sent_ok = 真实结果)。发送失败不重试(与现状同构)。窗口期进程重启:未发送的缓冲丢弃,事件已落库故不重报,`sent_ok=false` 读作「投递未确认」——诚实且可审计。
- **组评估**:每次 transition 后按厂商(family)维度重算:组内 alerted 端点数 / 组内 enabled 端点数 ≥50% 且 ≥2 → `group_down`;open 后占比回落 <50% → `group_recovered`。组 open 期间组内端点 transition 照常落事件、照常翻转 flag(端点级状态机独立完整),但**不进独立卡片**,作为组卡明细;组成员变动不再发新消息(与「故障持续保持沉默」同构)。组事件同样经窗口缓冲,flush 时组卡为主、未入组端点按 Hub 分节为次。
- **静默判定在 flush 与 score_drop 发送处**:静默期内只落事件不发送;静默结束时刻由同一时钟驱动一次检查,发 `quiet_summary`——仍 open 的端点(按 Hub 分节)+ 仍 open 的组 + 静默期内 score_drop 事件;空摘要不发。静默期 score_drop 事件落库、`sent_ok` 随摘要回写。**login_alert 完全豁免**:保持即时、off-lock 路径不动。
- 单实例、单 `mu` 锁、AfterRound 钩子语义全部保持(W5)。

### 时钟(W4)

- 窗口 flush 与静默边界检查由**可注入 Clock** 驱动;server 新增构造 Option(与 `WithNow` 同族的模式),生产接 RealClock,测试接假时钟手动推进。不引入 cron 库。

### API

- `PUT/GET /api/settings` 增加三个静默键(走既有 settings 通道,无新端点)。
- `GET /api/alerts` 事件增加 `group_key` 字段与新 kind 值(告警历史展示与审计)。

### 前端(web/)

- **OverviewGroupSection**:标头下方新增组级 24 格分段条(折叠恒显),着色沿用 §3 批 59 三档(≥95% 绿 / <95% 黄 / 0% 红 / 无数据灰),tooltip 与 EndpointCard dots 同构(「HH:mm 时段 · 成功 X/N」)。聚合走 utils 纯函数(与 StatusCard 批 59 口径同源:组内 enabled entries 的 dots_24h 按小时求和 ok/total),组件只渲染。
- **管理台设置表单**:静默时段启用开关 + 起/止小时选择(`el-switch` / `el-select` 用组件默认宽度,符合 §4 管理台表单限宽档)。
- **告警历史表**:新 kind 的中文标签(厂商组告警 / 厂商组恢复 / 聚合发送 / 静默摘要)。

### Lark 卡片

- down 聚合卡:red 模板,按 Hub 分节,Hub 内多端点标注「疑似 Hub 侧故障」;recovered 聚合卡:green 模板同构。组告警卡:red 模板 + 厂商名标题 + 组内明细(按 Hub 分节);组恢复卡:green 模板 + 已恢复/仍故障两节。静默摘要卡:red 模板(仍有故障是坏消息),各节同构。所有卡片保留 HubScope 签名 note。

### 显式行为变更(对现状)

- 单端点 down 告警从「即时发送」变为「≤60s 延迟」——这是聚合的统一代价,已经用户确认。
- 现有告警生命周期测试(`TestLarkAlertingLifecycle` 等)需在假时钟下改写:推进窗口后才断言消息到达;断言语义(迁移一次一条、持续沉默、恢复一条)保持不变。

## Testing Decisions

**什么是好测试(本项目纪律)**:只经 HTTP API 层断言外部行为——Lark stub 收到的消息条数/卡片内容、`GET /api/alerts` 的事件记录、设置接口的读回;不 mock 内部模块,不断言内部状态。

**唯一接缝 = W1 既有接缝**,不新增接缝:httptest + stub Hub + stubLarkServer + 真 SQLite 临时库,手动探测轮(`POST /api/endpoints/{id}/probe`)驱动状态迁移。**唯一新增**:经 server 构造 Option 注入假时钟(模式先例:`WithNow` / `WithSyncDiscovery`;假时钟先例:scheduler 测试),测试手动推进 60s 窗口与静默边界,消除一切真实等待。

**覆盖清单(黑盒)**:

- 窗口聚合:一轮内多端点 down → 推进 60s → 恰好 1 条聚合卡,按 Hub 分节含全部模型名;单端点 down → 60s 前 0 条、推进后 1 条。
- 恢复聚合:同窗口多恢复 → 1 条 green 卡;down 与恢复同窗 → 2 张卡。
- 组告警:构造 4 端点厂商组,2 个 down → 组卡 1 张(红,含厂商名与明细),组内第 3 个 down 不再发新消息;占比回落 → 组恢复卡列出仍故障端点;单端点组恒不触发;组触发前已发端点告警不回溯。
- 吸收语义:组 open 期间组内端点 down/恢复只落事件不发消息;组外端点照常聚合发送。
- 发送失败:stub 500 → 事件 `sent_ok=false` 落库,后续轮次不重发(现有先例 `TestAlertSendFailureRecorded` 扩展)。
- 重启:窗口内重启不重复告警(事件已落库);组 open 状态重启后正确重建,不重复组告警。
- 静默:时钟定在 23:30,端点 down → 0 条消息、事件照落;推进到 07:00 → 恰好 1 条摘要,只含仍故障端点;静默内自愈 → 摘要不提;空摘要不发;score_drop 期内延迟、随摘要送达;login 爆破期内照常即时(先例 `auth_bruteforce_alert_test.go`)。
- 配置:settings 读写三键;默认未启用时行为与现状一致;start==end 不启用。
- 告警历史:新 kind 与 `group_key` 经 `GET /api/alerts` 可见。

**前端 vitest**:组聚合纯函数(空组/全失败/混合/24 格小时对齐/与批 59 StatusCard 口径一致);分段条阈值着色与无数据灰;设置表单三态。

**回归**:全量 `make test`;既有 alert 测试在假时钟下改写后语义等价。

## Out of Scope

- 能力(capability)/协议(protocol)维度的分组告警(只锚定厂商)。
- 24h 可用率口径的分组告警(慢性侵蚀信号;本期只做急性整组故障)。
- 分组级 LatencySparkline(登记为后续候选)。
- Lark 消息编辑/跟进更新(首条立即发 + 后续合并跟进的形态已被否决)。
- 按组自定义阈值、按比例以外的触发规则;阈值(50%/2)与窗口(60s)冻结为常量,不做配置面。
- 静默时段按告警类型/按渠道细分(本期唯一豁免 = login);score_drop 以外的评估类通知。
- 告警认领、按端点/按组单独静默、移动端推送通道。

## Further Notes

### W5 承重墙四问(ADR 0014 骨架,实施阶段成文)

1. **为什么必须改**:单端点即时发送在 Hub 级故障下产生 N 条消息,告警可信度被轰炸磨损——W5 的存在目的(告警可信度)反而被现状损害;夜间无静默同理。
2. **影响哪些调用方**:`prober.AfterRound` 钩子语义不变(仍逐端点逐轮调用);`Evaluator.HandleRound` 内部从「判定即发送」改为「判定落库 → 窗口缓冲 → flush 发送」;score_drop 发送路径加静默门;login_alert 不动。
3. **有无替代方案**:① Lark 消息编辑跟进——被否决(消息量未实质减少,API 复杂);② 长窗口(3min)——被否决(急性故障感知变慢);③ 事件延迟落库——被否决(重启 60s 内会重复告警,直接违反 W5);④ 彻底吞掉静默期告警——被否决(丢现存故障信号)。
4. **回归测试什么**:既有生命周期测试在假时钟下的语义等价;重启不重复;持续故障沉默;发送失败落事件不重试;login 即时性。

### 落地顺序建议

分组 24h 分段条(纯前端,零风险)可独立先行;告警域三个机制(窗口 → 组告警 → 静默)共享同一次 alerter 改造,按此顺序切 ticket,每步可独立验证。
