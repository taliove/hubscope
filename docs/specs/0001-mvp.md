# HubScope — MVP Spec

> 状态:ready-for-agent。术语遵循 [CONTEXT.md](../../CONTEXT.md),架构决策见 [ADR-0001](../adr/0001-hub-credentials-in-database.md)、[ADR-0002](../adr/0002-endpoint-as-monitoring-unit.md)。

## Problem Statement

公司自建的 AI Hub(模型网关)接入了 26+ 个模型,向上游多家供应商转发。团队(Claude Code 及各类工具的使用者)经常遇到"某个模型又挂了/变慢了"却只能靠人肉发现的问题:

- 模型可能出现在 `/v1/models` 列表里但实际无可用上游(实测 `claude-opus-4-8` 走 openai 协议时报 `no_available_providers`),不实际调用就无法得知;
- 同一模型在 anthropic 与 openai 两种协议下可用性不同(实测 `gpt-5.4` 仅 openai 可用,`kimi-k3` 曾仅 anthropic 可用),消费方关心的正是协议级差异;
- 模型质量会随上游供应商调整悄悄劣化,没有任何机制做定期的质量对比;
- 没有地方能一眼看到"现在哪些模型能用、多快、质量如何"。

## Solution

一个对内的监控评估网站(Go 单二进制,内嵌 Vue 前端与 SQLite):

1. **可用性监控**:把每个 (Model × Protocol) 组合作为独立 Endpoint,每 5 分钟执行一轮 Probe(非流式 + 流式各一次),记录成败、延迟、TTFT、token 用量,产出红黄绿状态与趋势曲线;
2. **模型评估**:内置 4 个能力 Suite(基础指令遵循/推理数学/代码/中文),规则判定 + LLM 裁判混合打分,每周定时全量跑一轮,也可手动触发,产出可跨模型、跨时间对比的分数;
3. **告警**:Endpoint 连续失败或恢复时发飞书群机器人消息;
4. **管理后台**:Hub 实例、模型启停、Webhook、裁判模型等全部在线配置,无需改文件重启。

## User Stories

### 总览与状态

1. As a Hub 使用者, I want 打开网站就能看到所有 Endpoint 的红黄绿状态矩阵, so that 我在选模型前就知道哪些能用。
2. As a Hub 使用者, I want 看到每个 Endpoint 的 24h 成功率与 P50/P95 延迟摘要, so that 我不只看"能不能用"还看"快不快"。
3. As a Hub 使用者, I want 按模型名/协议/状态过滤状态矩阵, so that 模型多的时候能快速定位。
4. As a Hub 使用者, I want 不登录就能查看总览与详情页(内网), so that 查状态没有门槛。
5. As a Hub 使用者, I want 看到状态判定的依据(如"连续 3 次失败,最近错误:no_available_providers"), so that 我知道红是为什么红。

### Endpoint 详情与排障

6. As a 排障者, I want 查看单个 Endpoint 的延迟与 TTFT 随时间曲线, so that 我能判断是"整体慢"还是"卡住不出字"。
7. As a 排障者, I want 查看单个 Endpoint 的成功率趋势, so that 我能区分突发故障与渐进劣化。
8. As a 排障者, I want 查看近期的失败 Probe 记录及错误详情(HTTP 码、错误 message、session id), so that 我能拿着证据找 Hub 维护方。
9. As a 排障者, I want 切换查看流式与非流式请求的指标, so that 我能定位流式特有的问题。

### 模型与 Hub 管理

10. As an 管理员, I want 系统自动定期从 Hub 的 `/v1/models` 发现新模型并默认启用监控, so that 新模型上线无需人工登记。
11. As an 管理员, I want 从列表消失的模型被标记为下线但保留历史数据, so that 历史趋势可查且不误报。
12. As an 管理员, I want 手工添加不在 `/v1/models` 列表里的模型 ID(如 `claude-opus-4-8[1M]`), so that 列表外实际在用的变体也能监控。
13. As an 管理员, I want 逐 Endpoint 启停监控, so that 已弃用或误发现的组合不产生噪声和成本。
14. As an 管理员, I want 新模型接入时系统自动探测其支持的协议, so that 不需要人工判断该开哪条 Endpoint。
15. As an 管理员, I want 在管理后台增删改 Hub 实例(base URL、token),so that 换 Hub 或加 Hub 不用改文件重启。
16. As an 管理员, I want token 在界面上脱敏展示、接口不回传明文, so that 凭证不泄露。
17. As an 管理员, I want 为单个 Endpoint 覆盖探测间隔, so that 贵的大模型可以降频省钱。

### 告警

18. As a Hub 维护方, I want Endpoint 连续 3 次 Probe 失败时收到飞书群机器人告警(含模型、协议、错误摘要), so that 故障第一时间被发现而非等用户报障。
19. As a Hub 维护方, I want Endpoint 恢复时收到恢复通知, so that 我知道故障已结束。
20. As an 管理员, I want 在设置页配置/更换飞书 webhook 地址, so that 告警通道可调。

### 模型评估

21. As a Hub 使用者, I want 看到各模型在 4 个 Suite(基础指令遵循/推理数学/代码/中文)上的最新得分与排名, so that 我能按场景选最优模型。
22. As a Hub 使用者, I want 查看单个模型历次 Eval Run 的分数趋势, so that 我能发现上游悄悄劣化。
23. As a Hub 使用者, I want 查看单个 Case 的 prompt、模型作答与 Verdict 详情(含裁判理由), so that 我不只信分数还能看实际表现。
24. As an 管理员, I want 手动对指定模型 × Suite 触发一次评估, so that 新模型上线能马上出分。
25. As an 管理员, I want 每周定时自动全量评估, so that 分数保持新鲜无需人管。
26. As an 管理员, I want 配置 LLM 裁判用哪个模型(默认 `claude-opus-4-8`),so that 裁判可换、可控。
27. As an 管理员, I want 图像类等非对话模型(如 `gpt-image-2`)自动被排除在评估外, so that 不产生无意义的评估成本。
28. As an 管理员, I want 管理题库(浏览 Suite/Case、增改 Case 及其判定方式), so that 题库可持续扩充。
29. As a Hub 维护方, I want 可选地在某模型评估分数较上轮大跌时收到告警, so that 质量回退也能被及时发现。

### 认证与管理

30. As an 管理员, I want 管理操作(增改模型、改配置、手动触发评估)需要口令登录, so that 任意内网用户不能乱动配置、乱烧评估费用。
31. As an 管理员, I want 管理员口令通过环境变量/启动配置设置, so that 口令不进数据库、不进 git。

## Implementation Decisions

### 模块划分(Go 后端)

- **`hubclient`** — 调用 Hub 的 HTTP 客户端:三种能力(`ListModels`、`SendMessage` anthropic 协议、`ChatCompletion` openai 协议),支持流式与非流式,统一返回 {成功、HTTP 码、错误摘要、总延迟、TTFT、input/output tokens}。对 Hub 的唯一出口。
- **`prober`** — 对单个 Endpoint 执行一轮 Probe:非流式 + 流式各一次(同 Endpoint 内串行),产出两条 Probe 记录。请求内容:固定极短 prompt,小 max_tokens。
- **`scheduler`** — 定时驱动:每 5 分钟(单 Endpoint 可覆盖)调度所有启用 Endpoint 的 Probe,端点间并发上限 8;每小时驱动模型自动发现;每周驱动全量 Eval Run;每天驱动 rollup 与 90 天原始数据清理。所有间隔经由 `Clock` 接口,测试用假时钟。
- **`discovery`** — 拉 `/v1/models` 比对数据库:新模型自动建 Endpoint(自动试双协议,通的启用)、消失的标记下线(保留历史)。
- **`status`** — 状态判定机:最近一次失败→告警态;连续 3 次失败→Down(红);24h 成功率 <95% 或 P95 延迟超基线 2 倍→Degraded(黄);其余 Healthy(绿)。同时输出告警事件(第 3 次失败、恢复)。
- **`evaluator`** — 执行 Eval Run:对选定模型逐 Case 调用 Hub,按 Case 的 Verdict 方式判定(规则:精确/正则/包含;或 LLM 裁判按 rubric 打 0~1 分),按 Suite/维度聚合。跳过非对话模型。
- **`alerter`** — 出站 webhook 客户端(默认飞书群机器人格式),发送 Down/恢复/可选分数大跌消息。
- **`store`** — SQLite(modernc.org/sqlite 纯 Go 驱动,无 cgo)数据访问层,迁移内嵌。
- **`server`** — chi 路由 + JSON API + `go:embed` 内嵌前端产物;读接口公开,写接口要求管理员 session(口令登录,口令来自环境变量)。
- **`web`** — Vue 3 + Vite + TypeScript + Element Plus + ECharts,构建产物由 `server` 内嵌。

### 数据模型(SQLite,均带 hub_id 以支持多 Hub)

- `hubs`(id, name, base_url, token) — token 仅写入/校验用,读取接口脱敏。
- `models`(id, hub_id, model_id, discovered|manual, status: active|retired, capability: chat|non_chat, timestamps)
- `endpoints`(id, model_id, protocol: anthropic|openai, enabled, interval_override_seconds, consecutive_failures, current_status)
- `probes`(id, endpoint_id, streaming bool, ok, http_status, error_summary, latency_ms, ttft_ms, input_tokens, output_tokens, created_at) — 原始保留 90 天。
- `probe_rollups`(endpoint_id, bucket_start, bucket_size: hour|day, total, failures, p50_ms, p95_ms, avg_ttft_ms) — 永久保留。
- `suites`(id, key, name, version) — 内置 4 个:basic/指令遵循、reasoning/推理数学、coding/代码、chinese/中文;version 随 Case 增删/停用/替换递增。
- `cases`(id, suite_id, prompt, verdict_type: rule|judge, rule_config, rubric, difficulty: basic|intermediate|hard, sample_count NULL=跟随全局默认, enabled) — 不可变:PATCH 改题 = 新 Case + 停用旧 Case。
- `eval_runs`(id, suite_id, suite_version, trigger: scheduled|manual, judge_model, started_at, finished_at, status)
- `eval_results`(id, eval_run_id, model_id, case_id, answer_text, score 0~1, verdict_detail, latency_ms, tokens)
- `settings`(key, value) — webhook URL、裁判模型、告警开关、默认采样次数等运行期配置。
- `alert_events`(id, endpoint_id, kind: down|recovered|score_drop|score_drop_skipped, sent_ok, created_at)

### API 契约(JSON,`/api` 前缀;写操作要求 session)

- 读(公开):`GET /api/overview`(状态矩阵+24h 摘要)、`GET /api/endpoints/{id}`(详情+曲线数据+近期失败)、`GET /api/models`、`GET /api/suites`+cases、`GET /api/evals`(run 列表/分数对比)、`GET /api/evals/{id}`(逐 Case 详情)
- 写(需登录):`POST /api/auth/login`、`POST|PUT|DELETE /api/hubs`、`POST /api/models`(手工添加)、`PATCH /api/endpoints/{id}`(启停/间隔)、`POST /api/evals`(手动触发)、`PUT /api/settings`、`POST|PATCH /api/cases`

### 关键交互

- **Probe 固定 prompt**:非流式与流式均为极短指令(如 "Reply with: pong"),max_tokens 小;判定"成功"= HTTP 200 且解析出正常完成响应,不校验内容。
- **自动协议探测**:新模型发现时,对双协议各试一次极简请求,通的建启用 Endpoint,不通的建停用 Endpoint(可手动开)。
- **告警判定**:由 `status` 在连续失败计数达到 3 时产生 down 事件、由红转绿时产生 recovered 事件;`alerter` 只负责投递,不做判定。
- **LLM 裁判**:默认 `claude-opus-4-8`,经 Hub 调用;裁判 prompt 含 rubric,要求输出 0~1 分与理由;裁判失败该 Case 标记为未判分而非 0 分。
- **前端四个页面**:总览 Dashboard、Endpoint 详情、评估中心、管理与设置(登录后)。

## Testing Decisions

**唯一接缝:HTTP API 层黑盒测试。** 测试在进程内用 `httptest` 启动完整应用(路由+调度器+prober+评估器+真 SQLite 临时库),外挂两个替身:

1. **stub Hub HTTP server** — 模拟 `/v1/models`、`/v1/messages`、`/v1/chat/completions` 的成功/失败/慢响应/流式响应;
2. **假时钟** — `Clock` 接口注入,测试手动推进时间,驱动调度与"连续 3 次失败"等时序逻辑。

飞书 webhook 同为出站 HTTP,测试里换成 stub server 断言消息内容与时机。SQLite 用真库(临时文件),不 mock。

**好测试的标准**:只通过公开 API 驱动与断言(触发 Probe→查状态;触发 Eval→查分数;推进时钟→断言告警投递),不断言内部状态、不调用内部函数、不感知模块划分。内部重构不应导致测试改动。

**覆盖的核心行为**:模型自动发现(新增/下线/列表外手工添加)、双协议独立出状态、状态机(绿→黄→红→恢复)、Probe 指标记录(延迟/TTFT/token)、rollup 与 90 天清理、告警发送与去重、Eval Run 全流程(规则判定/裁判判定/聚合/裁判失败处理)、认证边界(读公开/写拒未登录)、token 脱敏。

**无既有测试先例**(全新项目),此模式即本项目的测试范式,后续功能沿用同一接缝。

## Out of Scope

- 前端单元测试与 E2E 框架(MVP 靠 TS 类型检查 + 构建验证)
- 多用户/角色权限体系、公司 SSO(只有单一管理员口令)
- 通用多通道告警(钉钉/Slack/邮件)——只做飞书 webhook
- 成本/价格统计(token 用量已记录,但不做计费与成本报表)
- 高可用多实例部署(单实例 + SQLite;多 Hub 是监控对象的多,不是部署的多)
- 图像/语音等非对话模型的质量评估
- Prometheus/Grafana 等外部监控栈集成

## Further Notes

- **凭证安全**:Hub token 与管理员口令一律不进 git;token 落库后任何读取接口脱敏。部署文档需说明口令经环境变量注入。
- **构建形态**:`go build` 产出单二进制(前端产物 `go:embed` 内嵌);提供 Makefile/脚本完成 `pnpm build → go build`;附带备选 Dockerfile。
- **部署**:内网 Linux 机器,systemd 常驻,nginx 反代内网域名;数据文件路径、监听端口、管理员口令走环境变量/启动配置。
- **探测成本**:26 模型 × 2 协议 × 2 请求 / 5 分钟 ≈ 每小时 1200+ 次极短请求,单次 token 消耗极小,成本可忽略;评估成本集中在每周一次的全量 Eval Run,受题库规模控制。
- **非目标提醒**:本系统只监控与评估,不做任何流量代理/改写;Hub 本身的问题只报告不修复。
