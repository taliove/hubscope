# 0012 — 自适应验证码登录(自托管图形码)

## 背景

spec 0011 已落地四道防线(per-IP 限流 5/min、per-账户渐进延迟、实例级爆破 Lark 告警、bcrypt + 统一错误消息),解决的是「爆破速度」。用户提出加验证码登录,补另一维度——**自动化本身**:撞库攻击(拿泄露密码本低速批量试)在现有限流下虽慢,但仍可无人值守运行;验证码强制每次尝试过人机区分,把机器人流量清零。两者叠加是完整形态:验证码挡机器人,渐进延迟拖慢分布式,告警让人知道。

用户已裁决两个形态问题:**自适应触发**(失败后才出验证码,合法用户日常无感)+ **自托管图形码**(不引入 Turnstile/reCAPTCHA 等外部服务——W8 单二进制自包含、内网测试线离线可验、生产在腾讯云 reCAPTCHA 不可用,外部方案三条全踩)。

## 决策总览

1. **触发口径(自适应):** 同一来源 IP **或** 同一用户名字符串,**10 分钟滑动窗口内登录失败 ≥2 次**后,该维度后续登录要求携带验证码——即第 3 次尝试起。两个维度独立判定,任一命中即要求;判定键与计数口径复用 spec 0011 决策 3 的失败观察点(用户不存在也计数,防枚举旁路)。登录成功清零该用户名与该来源 IP 的验证码计数(与渐进延迟计数各自的清零互不影响)。内存态,重启清零(spec 0011 已登记的接受界,此处同理)。
   - **共享出口登记:** 公司 NAT 后多用户共享 IP 时,一人失败 2 次会让该 IP 其他人也要验证码——可接受(验证码是轻交互,且任何一次成功登录即清零该 IP)。

2. **验证码签发(新端点):** `GET /api/auth/captcha`(公开,登录前无会话)返回 `{ captcha_id, image }`(image 为 PNG data URI)。答案存**内存 store**:key = 高熵随机 id,TTL 5 分钟,**一次性**——任何一次校验尝试(无论对错)即销毁。store 有硬上限 + 过期清扫(与 ipLimiter/loginDelayer 同族纪律),上限触达拒发新码(此时若客户端已被要求验证码,返回 503 而非静默放行——fail-closed,因为放行等于给攻击者免验证码通道)。

3. **登录契约变更:** `POST /api/auth/login` 请求体增加可选字段 `captcha_id` + `captcha_answer`。响应口径:
   - 被要求验证码而未携带/已销毁 → 401,body 带机器可读标记 `captcha_required: true`(前端据此展开验证码区);错误消息「请完成验证码」;
   - 验证码错误或过期 → 401 + `captcha_required: true`,错误消息「验证码错误或已过期」;
   - 其余失败路径不变(统一 "invalid credentials",无 `captcha_required` 标记时不改变现有前端行为);
   - 验证码校验**先于**密码校验(廉价先行);验证码失败**不计入**密码失败计数(未达密码校验,不构成密码尝试,不推进渐进延迟档位);未要求验证码时携带 captcha 字段一律忽略(不报错,兼容旧客户端)。

4. **签发接口限流(防打码靶场):** 验证码签发走独立限流档 **20 次/分钟/IP(burst 10)**——登录档 5/min 对「图片加载失败重试」太紧,读档 1200/min 则成了免费打码靶场。安全界推算:6 位数字码空间 10⁶,答案一次性、TTL 5 分钟,单 IP 每窗口最多 ~100 次有效猜测(20/min × 5min),穷举期望耗时以年计,且每次成功猜码仅换来一次密码尝试(仍受渐进延迟约束)——打码 brute force 不可行,登记为接受界。

5. **图形码选型:** Go 自托管库(base64Captcha 或同等),6 位数字图形码(干扰线/噪点),PNG。职责定位:抬自动化成本,非防定向人工破解,不为难真实用户(算术题/中文码/滑块不做)。**实现注意(登记):** 若库依赖外部字体文件,必须 go:embed 内嵌——单二进制约束(W8)不许运行时读字体文件。

6. **前端(LoginView):** 默认渲染现状(用户名+密码);收到 `captcha_required` 响应后展开验证码区(图形 img + el-input,**点击图形刷新**),展开后保持至登录成功;验证码相关错误消息内联展示(§5 表单校验失败内联,不用弹窗);登录页工具风与品牌区(§2b)不动。新交互开工前过设计评审(plan 的 UI 评审子能力,§0 纪律)。

7. **与既有防线的次序:** 请求路径次序 = per-IP 登录限流 → **验证码判定/校验** → per-账户渐进延迟计数与密码校验(spec 0011 挂点不变)→ 爆破告警计数(验证码失败是否计入实例级告警口径:计入——它仍是登录失败事实,与审计口径一致)。**验证码不替代任何一道既有防线。**

8. **可测试性:** captcha store 与签发限流档经 server option 注入(WithLoginDelay/WithRateLimits 先例),测试注入可预置答案的 store 与毫秒/个位数参数;不假时钟(W4 边界同 spec 0011)。

## 数据模型变更

无。验证码答案与触发计数均为进程内存态,不进 SQLite。

## 承重墙影响分析

本 spec 不修改任何承重墙,只消费:

- **W1(唯一测试接缝):** 全部新测试走黑盒接缝(httptest + 真 SQLite 临时库),captcha store 经 option 注入预置答案,测试不断言 store 内部。
- **W6(凭证边界):** 验证码答案不进任何日志/审计;`captcha_required` 标记与「验证码错误或已过期」按 IP/用户名双维度独立触发,不泄露用户名有效性(不存在的用户名同样计数同样要求,与 spec 0011 统一错误口径一致)。
- **W8(前端嵌入与单二进制):** 图形码纯 Go 生成,运行时零外部服务、零字体文件依赖(字体必须内嵌,见决策 5);不引入前端新依赖库(图形用 `<img>` data URI 渲染)。
- **W2/W4:** 零接触(内存态;不假时钟)。

## 测试决策

好测试 = 只观察外部行为(HTTP 状态码、`captcha_required` 标记、错误消息、响应时间量级),captcha 答案经注入 store 预置,不读内部状态。全部在 W1 接缝:

1. **触发的:** 同一用户名失败 2 次后,第 3 次不带验证码 → 401 + `captcha_required`;带错误验证码 → 401 + `captcha_required`;带正确验证码 + 正确密码 → 200。
2. **双维度独立:** IP 维度与用户名维度分别独立触发(换用户名不清 IP 的要求,换 IP 不清用户名的要求)。
3. **一次性:** 同一 captcha_id 第二次校验必败(即使第一次答案错误也已销毁)。
4. **TTL:** 注入短 TTL,过期后校验 → 「验证码错误或已过期」。
5. **验证码失败不推进延迟档:** 带错误验证码的失败不计入 per-账户渐进延迟计数(spec 0011 语义不被验证码路径绕过或加倍)。
6. **成功清零:** 登录成功后,该用户名与该 IP 的后续登录不再要求验证码(直至再次失败累计)。
7. **签发限流:** 注入小档位,超档 → 429。
8. **回归:** spec 0011 全部用例(渐进延迟、爆破告警、限流)零改动通过。

**测试先例:** `login_delay_test.go`(option 注入 + 黑盒时序)、`auth_bruteforce_alert_test.go`(失败观察点)、`security_test.go`(限流档)。

## 范围外

- 常驻式验证码(每次登录都要);
- Cloudflare Turnstile / reCAPTCHA 等外部人机验证服务;
- 滑块、点选、行为轨迹等高级人机验证;
- 登录页以外场景的验证码(无注册/找回密码功能,分享链接走 token 不走登录);
- 渐进延迟/限流/告警的既有参数调优(spec 0011 已定)。

## 备注

- 与 spec 0011 的关系:叠加不替代;两处失败计数(验证码触发 vs 渐进延迟)共用同一失败观察点但语义独立——验证码计数只管「要不要码」,延迟计数只管「罚多久」,清零路径各自独立。
- 若未来上 Turnstile(公网体验升级),自适应触发口径与本 spec 的登录契约(`captcha_required` 标记 + 双字段请求体)可直接复用,只换签发/校验实现——契约为升级预留了空间。
