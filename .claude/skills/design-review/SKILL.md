# 设计评审流程(事前)

适用触发(满足任一即必走):
- `web/src/views/` 新增视图;
- 引入新交互模式(新的弹窗/抽屉/导航/分区范式);
- 新增可复用组件(components/ 级);
- 修改语义色、状态表达方式或状态词表。

不属于以上档位的改动(bug 修复、数据对接、样式微调)不走本流程,直接按 frontend-dev 流程执行。

## 执行步骤

1. **准备输入:** 收集 ticket 需求、目标页面读者(状态板访客 vs 管理台管理员)、核心任务一句话、涉及的后端数据/接口。
2. **调用 design-owner 代理**,附上上述输入与改动范围;
3. design-owner 按 `.claude/rules/ui-guidelines.md` 评审并产出:
   - 结论:通过 / 有条件通过 / 打回;
   - 布局结构(区块划分、容器选型);
   - 组件选型(复用哪些既有组件、是否确需新组件);
   - 状态与语义色(引用规范 §3 条目);
   - 三态与交互反馈设计;
   - 文案要点(状态词、按钮词、错误消息);
   - 一致性风险标注(与既有页面模式的差异及理由)。
4. **处置结论:**
   - 通过 → 进入 frontend-dev 实现流程,评审意见作为实现约束;
   - 有条件通过 → 按条件调整方案后实现,不必复审;
   - 打回 → 修改方案后重新评审。
5. **回写规范:** 评审中确定的新约定(新组件登记、新语义映射、新文案词),由 design-owner 回写 `ui-guidelines.md`,不回写视为未约定。

## 输出格式

评审结果以 markdown 输出,包含:结论 / 逐条意见(规范条目号 + 理由)/ 建议方案 / 规范回写项清单。作者对评审意见需逐条回应(接受或说明不采纳理由),最终裁决权在用户。
